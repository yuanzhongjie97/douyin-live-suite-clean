## 6. 第 1 部分：业务背景

### 6.1 这一页标题

为什么需要这样一个工具？

### 6.2 这一页要讲什么

直播间运营过程中，人眼直接看公屏会遇到明显瓶颈：

- 消息滚动快，容易漏掉关键评论。
- 礼物消息和普通评论混在一起，观察成本高。
- 特殊身份用户不容易持续追踪。
- 重点用户出现时，需要第一时间被识别。
- 停播后需要导出数据复盘。
- 抖音未登录状态下，部分区域尤其是礼物区可能拿不到完整数据。

### 6.3 可直接讲稿

> 直播间数据不是静态页面，而是高频变化的数据流。
>
> 对运营来说，真正关心的不是页面上有没有消息，而是能不能快速看到关键消息，比如谁送礼了、谁进场了、谁评论了、神秘人有没有出现、特别关注用户有没有互动。
>
> 这些事情如果完全靠人工盯屏，会非常低效，而且一旦消息量上来，很容易漏数据。
>
> 所以这个项目的核心目标，就是把直播间里的动态数据采集下来，并按照运营视角重新组织和展示。

## 7. 第 2 部分：反推需求

### 7.1 这一页标题

糖三角要解决的核心需求

### 7.2 需求总览

可以用这一页展示：

```txt
登录采集
实时展示
重点用户高亮
神秘人追踪
噪音过滤
数据导出
桌面端交付
```

### 7.3 详细说明

#### 需求 1：登录后采集

要求：

- 用户必须先登录抖音。
- 登录后开始采集直播间。
- 登录状态要能复用，不能每次重新登录。
- 登录状态识别不能因为前端刷新延迟导致误判。

讲稿：

> 第一个需求是登录采集。这个很关键，因为礼物区在未登录状态下经常拿不到完整数据。所以我们不能只做一个匿名访问的采集器，而是必须复用用户真实登录后的浏览器环境。

#### 需求 2：直播数据分区展示

要求：

- 用户进场单独展示。
- 用户互动单独展示。
- 评论单独展示。
- 送礼单独展示。
- 最新消息要自动跟随。
- 用户手动暂停跟随时，不能强制滚动。

讲稿：

> 第二个需求是分区展示。原始直播间里，很多信息是混在一起的。我们把它拆成进场、互动、评论、送礼几个模块，让观察者可以按业务维度看数据。

#### 需求 3：神秘人识别

要求：

- 识别昵称、ID、主页链接中带“神秘人”的用户。
- 识别“神秘王者”。
- 普通用户 @ 神秘人时，不要误判普通用户是神秘人。
- 神秘人列表按最新活动倒序。
- 最多展示 99 个。
- 支持展开最近动态。
- 支持点击用户名访问主页。

讲稿：

> 神秘人模块是这个项目里业务规则比较复杂的部分。难点不是简单判断文本里有没有“神秘人”，因为普通用户也可能在评论里 @神秘人。如果只按评论内容匹配，就会误判。所以我们必须区分“发送者身份命中”和“评论内容提到了神秘人”。

#### 需求 4：特别关注

要求：

- 读取桌面 `highlight_users.txt`。
- 每行一个用户 ID。
- 支持备注。
- 支持部分通配符。
- 命中评论和送礼时高亮。
- 不展示完整关注列表，只展示命中消息。

讲稿：

> 特别关注的业务价值是快速识别重点用户。用户可以在桌面文件里配置 ID 和备注，软件启动后读取配置。之后这个用户只要评论或送礼，就会被高亮。

#### 需求 5：噪音过滤

要求：

- 过滤连线倒计时。
- 过滤纯数字倒计时。
- 过滤重复评论。
- 过滤系统提示类无效内容。

讲稿：

> 采集类项目很容易遇到一个问题，就是页面上看到的文本不一定都是业务消息。比如连线倒计时、系统提示、重复渲染内容，都可能被误采集。如果不处理，前端展示就会被垃圾数据污染。

#### 需求 6：导出和留存

要求：

- 停止采集后数据不清空。
- 支持 Excel 导出。
- 支持后续复盘。

讲稿：

> 实时观察只是第一步，采集结束后还要能复盘。所以数据不能只存在前端内存里，必须落到本地数据库，并且能导出 Excel。

## 8. 第 3 部分：整体技术架构

### 8.1 这一页标题

整体架构：桌面端 + 本地服务 + 浏览器采集

### 8.2 架构图

```txt
用户
  |
  v
Electron 桌面应用
  |
  |-- React 前端界面
  |-- Electron 主进程
  |
  v
本地 Fastify 服务
  |
  |-- 会话管理
  |-- 事件 API
  |-- SSE 实时推送
  |-- Excel 导出
  |
  v
Playwright Chromium
  |
  |-- 登录态浏览器 profile
  |-- 抖音直播间页面
  |-- DOM / payload 数据提取
  |
  v
SQLite 本地数据库
```

### 8.3 可直接讲稿

> 整体架构可以分成四层。
>
> 第一层是 Electron 桌面端，负责窗口、打包、本地能力和启动服务。
>
> 第二层是 React 前端，负责用户看到的所有界面，包括评论、送礼、神秘人、特别关注和版本日志。
>
> 第三层是本地 Fastify 服务，负责 API、SSE、采集会话管理、数据聚合和导出。
>
> 第四层是 Playwright 控制的 Chromium，它是真正进入抖音直播间并读取页面数据的地方。
>
> 最后所有重要事件会落到 SQLite，方便停止后保留和导出。

## 9. 第 4 部分：为什么这样选技术栈

### 9.1 Electron

选择原因：

- 需要 Windows 桌面应用。
- 需要本地文件读写。
- 需要打包成 EXE 和安装包。
- 需要管理窗口、子窗口、置顶、尺寸记忆。

不选纯 Web 的原因：

- 浏览器网页无法方便管理本地 Chromium profile。
- 本地文件、导出、数据库能力受限。
- 不适合长期运行的采集工具形态。

### 9.2 React

选择原因：

- 界面模块多，状态复杂。
- 适合快速构建交互界面。
- 能支持列表、弹窗、主题、实时刷新。

### 9.3 Fastify

选择原因：

- 轻量。
- 适合本地 API 服务。
- 和 Node/Electron 集成简单。
- 支持静态资源托管和 SSE。

### 9.4 Playwright

选择原因：

- 可以启动真实 Chromium。
- 支持持久化用户数据目录。
- 能复用登录态。
- 能执行页面脚本、读取 DOM、监听页面变化。

### 9.5 SQLite

选择原因：

- 本地单机软件，不需要部署数据库。
- 数据量可控。
- 查询统计方便。
- 适合会话和事件留存。

### 9.6 ExcelJS

选择原因：

- 运营人员常用 Excel。
- 导出后方便二次分析和复盘。

## 10. 第 5 部分：核心数据流

### 10.1 启动数据流

```txt
打开 EXE
  -> Electron 主进程启动
  -> 创建运行目录
  -> 查找可用端口
  -> 启动 Fastify 本地服务
  -> 加载 React 静态页面
  -> 前端请求状态接口
  -> 主界面可操作
```

讲稿：

> 启动时不是只打开一个页面。Electron 会先启动主进程，然后启动本地服务，再把 React 页面加载出来。所以启动速度会受到 Node 服务、前端资源、Chromium 运行时、安全扫描等多因素影响。

### 10.2 采集数据流

```txt
点击开始采集
  -> 后端校验登录态
  -> 创建 session
  -> Playwright 进入直播间
  -> Collector 提取原始事件
  -> parse / classify / filter
  -> 写入 SQLite
  -> 更新内存统计
  -> SSE 推送给前端
  -> React 批量渲染
```

讲稿：

> 一条直播评论从页面出现到界面展示，经过了采集、解析、分类、过滤、存储、推送、渲染多个环节。任何一个环节处理不好，都会导致误采集、延迟或卡顿。

### 10.3 神秘人数据流

```txt
采集到事件
  -> 判断身份字段是否包含神秘人/神秘王者
  -> 排除普通用户 @ 神秘人的误判
  -> 生成神秘人 identityKey
  -> 累加进场/评论/送礼计数
  -> 保存最近动态 activities
  -> 神秘人窗口按最新活动倒序展示
```

讲稿：

> 神秘人不是简单的关键词搜索，而是一个身份识别问题。我们关注的是“这个行为是不是神秘人本人发出的”，而不是“这条消息里有没有提到神秘人”。

### 10.4 特别关注数据流

```txt
读取 highlight_users.txt
  -> 解析 ID、备注、通配符
  -> 编译匹配规则
  -> 新消息进入前端
  -> 匹配用户身份字段
  -> 命中后高亮
  -> 弹窗展示命中消息
```

讲稿：

> 特别关注的关键是匹配范围。比如 `*dou*` 如果直接对整条 URL 或消息做匹配，就可能命中 `douyin.com`，导致全量高亮。所以规则必须限制在用户身份字段里。

## 11. 第 6 部分：关键难点与解决方案

### 11.1 难点一：登录态复用

问题：

- 未登录状态下，礼物区可能拿不到数据。
- 用户登录后，前端状态刷新可能有延迟。
- 登录窗口关闭后，仍需要复用浏览器 profile。

解决：

- 使用 Playwright persistent context。
- 浏览器 profile 本地持久化。
- 点击开始采集时，后端主动检查登录态。
- 前端不把“登录状态未刷新”作为唯一禁用依据。

讲稿：

> 这里有一个经验：登录态不能只靠前端显示状态判断。前端状态可能延迟，真正可靠的是后端在开始采集时再基于浏览器上下文做一次校验。

### 11.2 难点二：页面采集不稳定

问题：

- 抖音直播间页面结构可能变化。
- DOM className 不稳定。
- 礼物、评论、进场可能来自不同区域。
- 同一信息可能在多个节点里重复出现。

解决：

- 多源采集：DOM 文本、属性、payload、React 数据。
- 多级解析：先结构化字段，再文本解析。
- 分类函数统一判断 comment / entry / interaction / gift。
- 去重机制避免重复展示。

讲稿：

> 采集直播页面不能依赖一个固定选择器。页面一变，选择器就失效。所以我们采用的是多源提取和多级兜底，这样页面轻微变化时不至于整个采集失效。

### 11.3 难点三：噪音过滤

问题：

- 连线倒计时会被识别成评论。
- 主播页面上的纯数字倒计时会进入评论区。
- 系统提示会混入业务数据。

解决：

- 增加倒计时正则过滤。
- 对纯数字 0-180 做特殊屏蔽。
- 对 `(27s)`、`06:25` 等格式做过滤。
- 区分真实用户评论和页面 UI 文本。

讲稿：

> 采集不是拿到越多越好，而是要拿到对业务有意义的数据。噪音如果不过滤，软件看起来像采集很多，实际上是在干扰用户判断。

### 11.4 难点四：高频消息性能

问题：

- 评论和礼物高频进入时，前端渲染会卡。
- 列表 DOM 太多会拖慢窗口操作。
- 长时间运行后内存增长，窗口变卡。

解决：

- SSE 替代高频轮询。
- 前端批量处理消息。
- 列表保留数量限制。
- 评论和礼物去重。
- 虚拟列表降低 DOM 数量。
- 减少复杂 CSS 动画、阴影、滤镜。

讲稿：

> 高频数据场景下，性能问题不是某一个函数慢，而是采集、存储、推送、渲染共同造成的。我们的优化思路是减少刷新次数、减少 DOM 数量、减少重复数据、减少复杂样式。

### 11.5 难点五：神秘人误判

问题：

- 普通用户评论“@神秘人”时，不能把普通用户加入神秘人列表。
- 神秘人可能出现在评论、进场、送礼等多个模块。

解决：

- 优先判断身份字段。
- 评论内容提到神秘人但发送者身份不命中时，排除。
- 所有模块统一汇总到神秘人统计。
- 最新活动写入 activities，前端可展开查看。

讲稿：

> 神秘人模块的核心不是关键词，而是行为归属。我们要识别的是谁发出了这个行为，而不是一句话里有没有出现关键词。

## 14. 第 9 部分：项目复盘

### 14.1 做得比较好的地方

- 技术栈组合合理，适合桌面端直播采集场景。
- 登录态复用解决了礼物区采集问题。
- 神秘人和特别关注体现了业务规则沉淀。
- 数据最终能落库和导出，不只是临时展示。
- 高频消息场景下已经做了多轮性能优化。

### 14.2 踩过的坑

- 只看前端登录状态会误判登录结果。
- 简单关键词匹配会导致神秘人误判。
- `*dou*` 这种通配符如果匹配范围过大，会全量高亮。
- 页面倒计时会被误采集成评论。
- 数据量大后，UI 卡顿主要来自渲染和 DOM 数量。
- 打包图标、安装路径、启动速度这些工程细节也会影响交付体验。

### 14.3 后续优化方向

- 更稳定的图标写入和安装包工具链。
- 更彻底的列表虚拟化。
- 更完善的长期运行内存回收策略。
- 更强的采集规则自动适配能力。
- 更细粒度的性能监控面板。
- 更清晰的模块拆分和代码结构治理。

## 15. 可能被问到的问题

### Q1：为什么不用纯 Web 做？

答：

> 纯 Web 很难稳定管理登录态浏览器 profile，也不方便读写本地文件、SQLite、Excel 导出和打包成桌面软件。这个项目需要长期运行、本地存储和浏览器自动化，所以 Electron 更合适。

### Q2：为什么不用后端接口直接抓数据？

答：

> 直播平台接口复杂且容易变化，也涉及登录态、风控和权限问题。当前方案使用真实浏览器页面作为数据源，更接近用户实际看到的内容，也更容易复用登录状态。

### Q3：为什么 Chrome 占用内存高？

答：

> 直播间页面本身包含视频、图片、弹幕、礼物动画和大量前端脚本。Chrome 的资源占用主要来自直播网页本身，软件能优化的是减少额外页面、减少刷新、降低 UI 渲染成本，但不能完全消除直播网页的基础开销。

### Q4：为什么会出现重复评论？

答：

> 页面数据源本身可能重复渲染，同一条消息可能被不同 DOM 节点采集到。解决方式是基于用户、内容、时间窗口和 uniqueKey 做去重。

### Q5：神秘人为什么不能只按关键词匹配？

答：

> 因为普通用户可能评论或 @ 神秘人。如果只按内容关键词匹配，就会把普通用户误判成神秘人。必须判断行为发送者的身份字段。

### Q6：特别关注为什么不直接展示所有配置用户？

答：

> 这个功能的目标是提醒“命中消息”，不是管理用户列表。展示完整配置列表会占用界面空间，也不符合观察直播数据的核心场景。

### Q7：性能瓶颈在哪里？

答：

> 主要有三层：直播网页 Chrome 本身、采集和过滤逻辑、前端列表渲染。当前优化重点是前端批量刷新、去重、限制列表长度、虚拟列表和减少复杂样式。

## 16. 可直接使用的结束语

> 总结一下，糖三角不是一个简单的采集脚本，而是一个完整的桌面端实时数据工具。
>
> 它的难点不只是“把数据拿到”，更难的是拿到之后如何识别、过滤、去重、展示、导出，并且在长时间高频运行下保持可用。
>
> 这个项目给我的最大启发是：技术方案必须服务真实业务场景。很多问题不是框架能自动解决的，比如登录态、神秘人误判、特别关注匹配、倒计时噪音、性能卡顿，这些都需要从实际使用中不断修正规则。
>
> 后续如果继续优化，我会重点放在三个方向：采集规则稳定性、长时间运行性能、以及打包交付体验。
