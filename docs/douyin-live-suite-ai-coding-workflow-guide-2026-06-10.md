# 糖三角项目 AI Coding 运转闭环说明书

从需求、AI 协作、编码、测试、验收到文档沉淀的完整流程

- **生成日期**：2026-06-10
- **项目仓库**：github.com/yuanzhongjie97/douyin-live-suite-clean
- **适用对象**：用于个人熟读、简历项目复盘、面试前准备
- **阅读目标**：能用测试工程师视角讲清楚项目怎么从想法变成可验收的软件

## 一、先用一句话讲清楚这个项目

糖三角直播采集工具是一个个人 AI Coding 实践项目：通过 Codex/Claude 辅助完成 Windows 桌面工具的实现，用于采集抖音直播间公开可见的评论、进场、互动、礼物等数据，并支持实时展示、统计、特别关注、神秘人识别和 Excel 导出。

你在这个项目里的核心身份不是全栈开发工程师，而是软件测试工程师视角下的项目负责人：提出需求、确认边界、设计测试、验证质量、记录问题、复盘结果，并把过程沉淀成 PRD、风险报告、测试 SOP、测试报告和发布记录。

## 二、项目整体闭环图

这个项目不是只写了一个工具，而是跑通了一条完整闭环：需求想法 -> PRD -> 技术实现 -> 风险识别 -> 测试设计 -> 自动化/Mock 验证 -> 真实场景 smoke -> 用户验收 -> 文档同步 -> 版本发布。

| 阶段 | 你负责什么 | 产出物 |
| --- | --- | --- |
| 需求 | 提出真实使用场景，确认采集、展示、导出、特别关注等边界 | PRD、功能范围、验收标准 |
| AI 协作研发 | 使用 Codex/Claude 拆任务、读代码、改问题、补脚本 | 源码、脚本、安装包 |
| 测试设计 | 围绕主流程、异常流、边界数据设计测试场景 | 测试 SOP、覆盖矩阵 |
| 验证 | 用 mock 数据、回归脚本、真实直播间 smoke 验证质量 | 测试报告、问题记录 |
| 验收发布 | 确认版本号、发布边界、是否可用、是否阻断 | 发布记录、SHA256、迭代日志 |

## 三、需求从哪里来

项目需求来自真实使用问题，而不是为了展示技术而写代码。典型需求包括：直播间消息多，需要实时观察；评论、礼物、进场、互动需要分类；特别关注用户命中时需要高亮；采集结束后需要 Excel 复盘；直播间数据量大时界面不能明显卡顿。

这些需求被整理到 PRD 中，明确了 In Scope 和 Out of Scope。例如：支持 Windows 桌面端、本地服务、Playwright 采集、SQLite 本地持久化、Excel 导出；不做云端服务、不接抖音官方 API、不做移动端 App、不绕过登录。

## 四、AI Coding 在项目里怎么用

AI Coding 的作用不是替代你理解业务，而是帮助你把需求变成代码、测试和文档。你需要告诉 AI：要解决什么问题、不能破坏什么功能、边界怎么定、验收标准是什么。AI 负责读代码、提出方案、修改实现、补测试、更新文档，你负责拍板和验收。

| 环节 | 你和 AI 的配合方式 |
| --- | --- |
| 需求拆解 | 你描述业务目标和边界，AI 整理 PRD、风险点和测试项 |
| 代码修改 | 你说明要修什么、不能影响什么，AI 读取代码后局部修改 |
| 测试补强 | 你确认核心质量目标，AI 补 mock 数据、回归脚本和测试 SOP |
| 问题复盘 | 真实使用发现问题后，你反馈现象，AI 定位原因、修复并记录 |
| 文档同步 | 每次修复后，把 PRD、风险报告、测试报告、发布记录同步更新 |

## 五、技术架构用测试视角怎么理解

你不需要把自己包装成这些技术栈的专家，但要能说明它们在项目里的作用。面试时可以说：项目采用这些技术栈实现，自己主要负责需求边界、测试验证和验收闭环。

| 技术 | 一句话理解 |
| --- | --- |
| Electron | 把前端页面和本地服务打包成 Windows 桌面软件 |
| React/Vite | 实现主界面，展示评论、礼物、统计、特别关注等数据 |
| Fastify | 本地后端服务，给前端提供接口和实时事件流 |
| Playwright | 打开抖音登录页和直播间页面，辅助采集公开可见数据 |
| SQLite | 本地数据库，保存会话、事件和统计数据 |
| ExcelJS | 把采集结果导出为 Excel 文件 |
| Node 回归脚本 | 自动验证核心功能，减少手工回归遗漏 |

## 六、核心功能怎么运转

主流程可以拆成 7 步：启动桌面客户端；打开登录窗口完成抖音登录；输入直播间 URL；开始采集；前端实时展示评论、进场、互动、礼物；停止或关播后保存会话；导出 Excel 用于复盘。

| 功能模块 | 测试关注点 |
| --- | --- |
| 启动 | 主界面不白屏，本地服务监听本机地址 |
| 登录 | 登录窗口可打开、可关闭、采集中不误操作 |
| 开始采集 | 只允许合法直播间 URL，未登录时给出错误 |
| 实时展示 | 评论/礼物/进场/互动分类正确，高频数据下界面可用 |
| 特别关注 | 命中时高亮，备注展示正确，原昵称不被备注覆盖 |
| 导出 Excel | 停止后数据仍保留，Excel 可打开，包含统计和分类 sheet |

## 七、测试 SOP 是怎么设计的

测试 SOP 的核心思路是：不要只依赖真实直播间，因为真实直播间不可控；要用 mock 数据和回归脚本覆盖稳定场景，再用真实直播间做 smoke 验收。

| 测试类型 | 作用 |
| --- | --- |
| 功能测试 | 验证登录、采集、展示、停止、导出等主流程 |
| 接口/安全边界测试 | 验证非法来源、异常请求不会误触发本地 API |
| Mock 数据测试 | 构造评论、礼物、特别关注等数据，验证展示和导出 |
| 回归脚本 | 每次改动后自动跑核心用例，降低改坏旧功能的风险 |
| 真实 smoke | 用真实直播间跑一遍主流程，确认安装版可用 |

## 八、Mock 数据和回归脚本怎么理解

Mock 数据就是构造假的评论、礼物、进场、互动等事件，不依赖真实直播间，也能验证功能逻辑。例如：构造一条礼物数据，看礼物名和数量是否展示正确；构造一条特别关注用户数据，看是否高亮和弹窗；构造大量事件，看统计和导出能否完成。

回归脚本就是自动执行一批检查。项目里按 server、web、desktop 分层运行：server 侧验证 API、数据库、导出和采集归一化；web 侧验证前端展示和特别关注；desktop 侧验证版本、白屏诊断、安装包资源等。

## 九、真实直播间 smoke 是什么

Smoke 验收不是完整测试，而是发布前快速确认主流程能跑通。这个项目里的真实 smoke 包括：安装软件、启动无白屏、确认登录状态、输入直播间 URL、开始采集、观察是否有评论/礼物/进场/互动、停止采集、导出 Excel、打开文件确认可读。

真实 smoke 的价值是贴近用户场景；局限是直播间数据不可控，所以它不能替代 mock 和回归脚本。简历和面试中可以说：真实 smoke 用于增强发布信心，不作为唯一质量依据。

## 十、10 万事件压测怎么讲

10 万事件压测不是让真实直播间刷出 10 万条数据，而是用脚本构造 mock 事件，批量写入临时 SQLite 数据库，再验证统计和 Excel 导出是否能完成。它验证的是存储、统计和导出链路的承载边界。

脚本会分别构造 1 万、5 万、10 万事件，事件类型包括评论、进场、互动、礼物、日志。每批写入后检查统计总数、读取导出数据、生成 Excel 文件，并记录耗时、文件大小和内存变化。

面试里可以这样说：我了解它的测试目的和验证链路，但不把它包装成真实直播间全量采集能力。它主要帮助确认当前设计在大数据量下是否有明显风险。

## 十一、风险报告在闭环里起什么作用

风险报告不是为了写文档，而是为了决定先修什么、哪些暂时接受、哪些需要用户拍板。项目里把风险分成 P0/P1/P2：P0 是影响可用性或安全边界的问题，必须优先处理；P1 是重要但不一定阻断发布；P2 是长期维护和体验优化。

| 风险例子 | 处理方式 |
| --- | --- |
| 本地 API 来源风险 | 用回归测试验证非法来源不会误访问本地接口 |
| Electron 安装后启动报错 | 修复打包链路并补安装启动验证 |
| 大直播间数据边界 | 用 mock 压测判断统计和导出压力 |
| 特别关注展示口径 | 由用户拍板，只改展示，不动采集和导出逻辑 |
| 代码签名/CI | 当前不做，记录为后续改进项 |

## 十二、验收和发布怎么闭环

每次版本发布前，不只是打包，还要确认版本号、回归结果、安全审计、安装启动、真实 smoke、Excel 导出和发布记录。项目版本号按日期约定，例如 V26.6.10.2 表示 2026 年 6 月 10 日第 2 个版本。

用户负责最终业务验收和是否发布的拍板；AI 协作完成修复、测试和文档同步。这个边界很重要：AI 不能替你决定业务是否可接受，最终质量判断仍由你根据测试结果和使用反馈确认。

## 十三、你在面试中怎么讲

推荐讲法：这是我的个人 AI Coding 实践项目。我不是以全栈开发工程师身份包装它，而是通过 Codex/Claude 辅助实现工具，自己负责需求梳理、测试设计、mock 数据验证、真实直播间 smoke、问题复盘和文档闭环。项目采用 Electron、React、Fastify、Playwright、SQLite 等技术栈，我能解释它们在项目里的作用，但我的主要贡献是软件测试和质量保障。

不要讲成：我精通 Electron、React、Fastify，独立完成所有底层安全设计和性能压测。更稳的表达是：我能使用 AI 工具理解和协作推进这些技术实现，并围绕业务质量设计验证方法。
